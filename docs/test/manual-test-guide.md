# 手動テストの手引き (最終確認用)

この文書は、最後の手動テストを行う人のための手引きです。
使う道具は「手動テスト支援ツール」(`tools/ManualTestRunner`) です。
テストケースは `docs/test/cases/*.md` にあり、ツールが直接読みます。

## 1. 件数と所要時間

手動と半自動のテストケースは、全部で 109 件です (手動 88 件、半自動 21 件)。
フェーズ 0〜5 のすべてを含みます。
所要時間の目安の合計は約 403 分 (約 6 時間 40 分) です。

| グループ | 内容 | 件数 | 目安 |
| --- | --- | --- | --- |
| A | この PC だけでできる | 51 件 | 165 分 |
| B | 機材や別の環境が必要 | 47 件 | 195 分 |
| C | 保留 (公開・署名のあとでないとできない) | 11 件 | 43 分 |

B のうち、できれば行うもの (推奨) は 24 件・約 101 分です。
なくてもよいもの (任意) は 23 件・約 94 分です。
機材がなければ「対象外」にして構いません。

## 2. ツールのビルドと起動

PowerShell をリポジトリのルート (`f:\dev\HexEditor`) で開き、次を順に実行します。

```powershell
git switch main
git pull
dotnet build src/HexEditor.App/HexEditor.App.csproj -p:Platform=x64
dotnet build tools/ManualTestRunner -p:Platform=x64
```

1 つ目のビルドは、テストする HexEditor 本体を作ります。
2 つ目のビルドが、手動テスト支援ツールです。

ツールを起動します。

```powershell
& "tools\ManualTestRunner\bin\x64\Debug\net10.0-windows10.0.26100.0\win-x64\ManualTestRunner.exe"
```

ツールは、ビルドした HexEditor (`src\HexEditor.App\bin` の下の最新の `HexEditor.exe`) を自分で探します。
見つからないときは、環境変数 `HEXEDITOR_EXE` に `HexEditor.exe` のパスを入れてから起動します。

```powershell
$env:HEXEDITOR_EXE = "C:\...\HexEditor.exe"
```

注意:

- ツールのウィンドウは、既定で「常に手前に表示」になります。邪魔なときは「常に手前に表示」のチェックを外します。
- 結果は `%LOCALAPPDATA%\HexEditorManualTests` に自動で保存されます。途中で閉じても、次回は続きから再開できます。

## 3. 全フェーズの手動・半自動を選ぶ

ツールの左上で、次のように選びます。

1. 「テストの選び方」を「リリース前 (すべての手動・半自動)」にする。最初は「スモーク」になっているので、必ず変える。
2. 「フェーズ (以下)」を「5」にする (既定で 5)。
3. 「機能 ID」の欄は空にする。

これで 109 件が一覧に出ます。
一覧の下に「109 件 / 合計 約 403 分」と表示されます。

一部だけ行うときは、「機能 ID」の欄に文字を入れて絞ります。

| 入力 | 出てくるもの |
| --- | --- |
| `FOR-` | フォレンジックのテスト (USB メモリなど) |
| `PKG-` | 配布のテスト |
| `ENG-28` | 管理者権限の補助プロセスのテスト |
| `TC-UI-` | UI のテスト |

「未実施のもの」を選ぶと、まだ結果を付けていないものだけが出ます。
「前回不合格・保留のもの」を選ぶと、やり直しが必要なものだけが出ます。

## 4. 1 件ごとの進め方

1. 一覧からテストケースを選ぶ。
2. 「環境」「前提」を読む。必要な機材がなければ、「対象外」を押して次へ。
3. 「準備」ボタンを押す。テストデータを作り、HexEditor を起動します。
   - 起動した HexEditor は一般の権限です。管理者として行うテストでは、いったん閉じ、`HexEditor.exe` を右クリックして「管理者として実行」で起動し直します。
   - 設定は専用のフォルダ (`--test-profile`) に置かれます。普段の設定は変わりません。
4. 「手順」を 1 つずつ行い、チェックを付ける。
5. 「期待結果」と見比べて、「合格」「不合格」「保留」「対象外」のどれかを押す。
6. 不合格のときは、コメントに気づいたことを書く。画面とログと環境の情報は自動で付きます。

結果の使い分けです。

| 結果 | 使うとき |
| --- | --- |
| 合格 | 期待結果のとおりだった |
| 不合格 | 期待結果と違った。コメントに何が違ったかを書く |
| 保留 | 今はできないが、あとで行う。コメントに理由と、できるようになる条件を書く |
| 対象外 | 機材や環境がなく、行わない。コメントに「機材なし」などと書く |

## 6. 壊れてもよい機材だけを使う (破壊を伴うテスト)

次のテストは、USB メモリの中身を消したり、書き換えたりします。

- TC-FOR-24-04 (クローン)
- TC-FOR-25-03 (セクタの復元)
- TC-FOR-30-05 (ディスク全体の消去)

TC-FOR-20-07 は読み取るだけです。TC-FOR-27-04 などの SATA のテストも読み取るだけです。

守ること:

1. 中身が消えてよい USB メモリだけを使う。大切なデータが入ったものは使わない。
2. 行う前に、ほかの USB ディスクと外付けディスクをすべて抜く。
3. 対象のディスクを、PowerShell で必ず確かめる。

   ```powershell
   Get-Disk | Format-Table Number,FriendlyName,BusType,Size
   ```

   - 「BusType」が USB のものが USB メモリです。
   - 「FriendlyName」と「Size」が、手元の USB メモリと合っていることを確かめます。
   - システムのディスク (通常は 0 番。BusType が NVMe か SATA) は、絶対に選びません。
4. ディスク番号 N を紙かメモに書く。HexEditor のダイアログに出るディスク番号・名前・容量が、書いたものと同じか、もう一度見る。
5. 強い確認のダイアログで、`ディスク N` と入力するまで実行ボタンが押せないことを確かめる。違う番号では押せないことも確かめる。
6. 少しでも迷ったら「キャンセル」を押す。そのテストは「保留」にする。
7. 終わったら、ディスクの管理で USB メモリを初期化し直す。

読み取り専用のテストでも、ディスクの番号を確かめる習慣は同じです。

## 7. 結果を書き出して Claude に送る

1. ツールで、「テストの選び方」を「リリース前 (すべての手動・半自動)」、「フェーズ」を 5、「機能 ID」を空にする。書き出しは、いま一覧に出ているものだけが対象です。
2. 「報告を書き出す」を押す。
3. ダイアログに、書き出した場所が出る。通常は `%LOCALAPPDATA%\HexEditorManualTests` の `report-日時.md` と `report-日時.json` です。
4. 2 つのファイルを Claude に渡す (チャットに貼るか、パスを伝える)。不合格のスクリーンショットは、同じフォルダの `screenshots` にあります。

不合格のものは、Claude が GitHub の Issue の下書きにします。送信は、あなたが確かめてから行います。
最初からやり直したいときは「新しく始める」を押します。前回の結果は `run-日時.json` に残ります。

## 8. 注意

- HexEditor のウィンドウを、別のアプリの上に無理に出さないでください。テストの間は、ツールの「常に手前に表示」を使います。
- クリップボードを使うテストでは、他のアプリのコピーしたものが消えます。終わってから他の作業をしてください。
- テストでレジストリや設定を変えるものは、ありません。ただし、TC-FOR-02-01 は Windows の USB 書き込み保護の設定を変えます。手順の最後で必ず無効に戻します。
- 手順のとおりにできないとき (ボタンの名前が違うなど) は、「不合格」にして、コメントに見たものをそのまま書きます。
