# テスト仕様書: 方針と共通ルール

この文書は HexEditor のテストの進め方を定める。テストケースそのものは `cases/` 以下に、機能仕様書 ([../spec/](../spec/00-overview.md)) と同じ分け方で置く。

## 1. 目的

1. 機能仕様書のすべての受け入れ基準 (1,847 項目、2026-10-07 時点) を、少なくとも 1 つのテストケースで確認する。
2. 自動化できるテストはすべて自動化し、プルリクエストごとに CI で実行する。
3. 手動でしか確認できないテストは、準備・実行・記録の手間を最小にして、短時間で漏れなく実行できるようにする。

## 2. 構成

| ファイル | 内容 |
| --- | --- |
| [00-test-strategy.md](00-test-strategy.md) | 方針と共通ルール (この文書) |
| [test-data.md](test-data.md) | テストデータの一覧 (テストデータ生成ツールが作るファイル) |
| `cases/01-engine-and-sources.md` 〜 `cases/12-forensics.md` | テストケース。機能仕様書の 01〜12 と 1 対 1 に対応する |

### 2.1 テストケースの数 (2026-10-07 時点)

| 種別 | 件数 |
| --- | --- |
| 自動 | 1,667 |
| 半自動 | 21 |
| 手動 | 69 |
| 合計 | 1,757 |

- 手動・半自動の所要時間の合計は約 318 分。そのうちスモークテスト (優先度「高」) は約 45 分。
- 1,847 項目の受け入れ基準のすべてに、1 つ以上のテストケースが対応している。

## 3. テストの種類

| 種別 | 対象 | 道具 | 実行のタイミング |
| --- | --- | --- | --- |
| 自動: 単体 | `HexEditor.Core` のクラス単位 (データエンジン、検索、入力式の解釈、形式の変換、ハッシュなど) | xUnit、FsCheck (性質ベースのテスト) | プルリクエストごと |
| 自動: 結合 | 複数の部品の組み合わせ、実際のファイル・ディスク・プロセスを使う処理 (保存、外部変更の検知、補助プロセス、コマンドライン) | xUnit、テスト用のファイル・仮想ディスク (VHDX)・テスト用プロセス | プルリクエストごと |
| 自動: UI | 画面の操作と表示 (キー操作、メニュー、ダイアログ、パネル) | FlaUI (UI オートメーション) | プルリクエストごと (主要なもの)、毎晩 (すべて) |
| 自動: 性能 | 00-overview 11.1・11.2 の数値目標 | BenchmarkDotNet、計測用のテスト | 毎晩 |
| 自動: 国際化 | 23 言語の表示、疑似翻訳、右から左、地域設定 | FlaUI によるスクリーンショット撮影と自動判定 | 毎晩 |
| 自動: アクセシビリティ | UI オートメーションの構造、名前の欠落、コントラスト | Axe.Windows | 毎晩 |
| 自動: ファジング | 外部データを解釈する部分 (Intel HEX、テンプレート、ファイルシステム解析、パッチ形式) | SharpFuzz | 毎週 |
| 自動: 配布 | 3 種類の配布物のインストール・起動・更新・アンインストール | GitHub Actions の Windows ランナー | リリース前、毎晩 |
| 半自動 | 準備と操作は自動、合否の判断だけ人が行う (見た目の確認など) | 手動テスト支援ツール (8 章) | リリース前 |
| 手動 | 人の操作・判断・実機が必要なもの | 手動テスト支援ツール (8 章) | リリース前 |

### 3.1 自動化の判断基準

受け入れ基準は、次のどれかに当てはまる場合だけ手動 (または半自動) にする。それ以外はすべて自動にする。

| 手動にする理由 | 例 |
| --- | --- |
| 人の目でしか判断できない | 文字のにじみ、配色の見やすさ、アニメーションの自然さ |
| 実機・実環境が必要で、CI で再現できない | USB メモリの抜き差し、SMART 情報、ARM64 の実機、Windows 10 の実機 |
| OS の安全機能が自動操作を拒否する | UAC の確認画面、SmartScreen の警告 |
| 外部サービスが必要 | Microsoft Store への提出・Store からの更新、winget |
| 支援技術での実際の体験 | ナレーター・NVDA での読み上げの聞き取り |

- 手動にしたテストケースには「手動にする理由」を必ず書く。理由が上の表に当てはまらない場合は自動にする。
- 一部だけ人の判断が必要なものは、自動で状態を作ってスクリーンショットを撮り、人は画像を見て合否だけ付ける「半自動」にする。

## 4. テストケースの書式

### 4.1 ID

- `TC-<機能 ID>-<連番 2 桁>` とする (例: `TC-ENG-01-01`)。
- 1 つの受け入れ基準に 1 つ以上のテストケースを対応させる。1 つのテストケースが複数の受け入れ基準を確認してもよい。
- 一度付けた ID は変えない。廃止したテストケースは「廃止」と書いて ID を残す。

### 4.2 書式

```markdown
### TC-ENG-01-01 テストケース名

| 項目 | 内容 |
| --- | --- |
| 確認する基準 | ENG-01 の受け入れ基準 1、2 |
| 種別 | 自動: 単体 |
| 優先度 | 高 |
| フェーズ | 0 |
| テストデータ | TD-SPARSE-100G |
| 環境 | 標準 |

**前提**: テストの開始時の状態。

**手順**:

1. 操作を 1 行に 1 つ、具体的な値で書く。

**期待結果**:

- 確認できる形で書く。
```

| 項目 | 書き方 |
| --- | --- |
| 確認する基準 | 機能 ID と受け入れ基準の番号 (機能の「受け入れ基準」の上から数えた番号) |
| 種別 | 3 章の種別のどれか 1 つ |
| 優先度 | 高 (スモークテストに入れる。壊れると基本操作ができない)、中、低 |
| フェーズ | 対象の機能のロードマップのフェーズ (0〜5)。確認する基準がほかの機能 (後のフェーズの機能を含む) に依存するときは、対象の機能のフェーズと、依存する機能のフェーズのうち遅いほうを書く |
| テストデータ | [test-data.md](test-data.md) の ID。不要なら「なし」 |
| 環境 | 「標準」(5 章) 以外の条件があれば書く (例: 管理者として実行、USB メモリ、アラビア語表示、ARM64) |

- 手動・半自動のテストケースには、さらに「手動にする理由」と「所要時間の目安」(分) を表に加える。
- 自動のテストケースの「手順」は、テストコードが行うことを書く。テストコードのクラス・メソッド名は書かない (コード側にテストケース ID を付けて対応させる。6 章)。

### 4.3 手動テストケースの書き方の決まり

手作業でスムーズに実行できるよう、手動・半自動のテストケースは次を守る。

1. 手順は 1 行に 1 操作。キーは `Ctrl+G` のように書き、メニューは「ファイル > 開く」のように書く。
2. 入力する値・開くファイルはすべて具体的に書く。「適当なファイル」のような書き方はしない。ファイルはテストデータの ID で指定する。
3. 期待結果は、画面上で目で見て確認できることだけを書く。確認する場所 (ステータスバー、ダイアログの文言など) を明記する。
4. 1 つのテストケースは 10 手順以内、5 分以内に終わる大きさにする。長くなる場合は分ける。
5. 前のテストケースの結果に依存させない。前提の状態は、手動テスト支援ツールの「準備」(8.2) で作れるように書く。
6. 期待結果の文言は英語表示と日本語表示の両方で確認できるように、メッセージは仕様書の意図で書く (訳文そのものに依存させない)。

## 5. テスト環境

### 5.1 標準環境

| 項目 | 内容 |
| --- | --- |
| OS | Windows 11 (最新の一般提供版)、x64 |
| 表示言語 | 英語 (en-US)。手動テストは日本語でもよい |
| 表示倍率 | 100% |
| 配布形態 | ポータブル版 (テスト用の設定フォルダを使う。8.3) |
| 権限 | 一般ユーザー |

### 5.2 環境の組み合わせ

すべてのテストを全環境で行うことはしない。次の表の「対象」だけを各環境で行う。

| 環境 | 対象 | 方法 |
| --- | --- | --- |
| Windows 10 22H2 x64 | スモークテスト (優先度「高」) と配布のテスト | 手動 (仮想マシン) |
| Windows 11 ARM64 | スモークテスト | 手動 (実機または仮想マシン) |
| インストーラ版 / ポータブル版 / Store 版 | 配布のテスト、配布形態で動作が変わる機能 (設定の保存先、Explorer 連携、管理者権限) | 自動 (CI) と手動 |
| 23 言語 | 国際化のテスト | 自動 (毎晩) |
| アラビア語・ペルシア語 (右から左) | 国際化のテストと、主要画面の手動確認 | 自動と半自動 |
| 表示倍率 100% / 150% / 200% / 400% | UI のテスト (主要画面) | 自動 (スクリーンショット) と半自動 |
| ハイコントラスト | アクセシビリティのテスト | 自動と半自動 |
| 管理者として実行 | ディスク・プロセスメモリのテスト | 自動 (CI のランナーは管理者権限で動く) と手動 |
| 一般ユーザー (CI) | 補助プロセス経由の管理者権限の処理 (ENG-28 など) | 自動。CI の管理者権限のランナー上で、アプリを権限を落としたトークンで起動し、UAC を「確認なしで昇格」に設定する。これで補助プロセスの起動と通信を自動で確認できる。UAC の確認画面そのものの表示だけは手動で確認する |

## 6. 自動テストの作り方

### 6.1 プロジェクト構成

```text
tests/
  HexEditor.Core.Tests/          単体テスト
  HexEditor.Platform.Tests/      配布形態・実行環境・版・インストールのフック・ビルドのスクリプトの単体テスト (10 の PKG)
  HexEditor.Integration.Tests/   結合テスト (ファイル・ディスク・プロセス・コマンドライン)
  HexEditor.UI.Tests/            UI テスト (FlaUI)
  HexEditor.Performance.Tests/   性能テスト (BenchmarkDotNet と計測テスト)
  HexEditor.Fuzz/                ファジング
tools/
  TestDataGen/                   テストデータ生成ツール (7 章)
  ManualTestRunner/              手動テスト支援ツール (8 章)
  TestTarget/                    プロセスメモリのテストに使う小さなプロセス
```

### 6.2 テストケースとの対応付け

- 自動テストのメソッドには、確認するテストケース ID を属性で付ける (例: `[TestCase("TC-ENG-01-01")]`。xUnit では `[Trait("TC", "TC-ENG-01-01")]`)。
- 種別が「自動: 配布」で、ビルドした配布物を調べる・起動する・インストールするテストは、xUnit ではなく `build/tests/` の PowerShell のスクリプト (Pester は使わない) にする。各テストは `Invoke-TestCase '<テストケース ID>' '<名前>' { ... }` で書き、CI のジョブ (`ci.yml` の artifacts・portable、`release.yml` の verify) が実行して結果の表をジョブの概要に出す。開発者の PC で実行するとウィンドウが開く・インストールされるため、CI のランナーだけで実行する。
  - `Test-Artifacts.ps1`: 配布物の中身 (ビルドするだけで確かめられるもの)
  - `Test-Portable.ps1`: ポータブル版を展開して起動するもの
  - `Test-Installer.ps1`: インストーラ版をインストール・アンインストールするもの
  - `Test-Distributions.ps1`: 3 種類の配布形態 (1 つのアーキテクチャ) を入れて起動するもの (`ci.yml` の distribution。x64 と ARM64 のランナー)
  - `Test-Msix.ps1`: MSIX 版をテスト用の証明書で入れるもの (`ci.yml` の msix)
  - `Test-SameResults.ps1`: 3 種類の配布形態で実行した UI テストの結果を突き合わせるもの (`ci.yml` の ui-distro・same-results)
  - `Test-Release.ps1`: リリースのワークフローが作ったリリースを調べるもの (`release.yml` の publish)
  - アプリを操作するテストは、テスト用のビルド (`build/publish.ps1 -TestHooks`) をテスト用の命令の通り道 (7.2) で操作する (`AppDriver.ps1`)。まだない機能に依存する手順は `Skip-TestCase` (理由を付けて「Skipped」) か `Add-TestNote` (「Not checked」の一覧) で示し、失敗にしない。環境変数 `HEX_TEST_CASES` にテストケース ID を並べると、そのテストケースだけを実行する。
- CI はテストの結果とテストケース ID を突き合わせ、次を一覧にしたレポート (`test-coverage.md`) を作る。
  - 種別が「自動」なのに、対応する自動テストがないテストケース
  - どのテストケースにも対応しない受け入れ基準
  - 失敗したテストケース

  一覧は `tools/TestCoverage` が機能仕様書・テストケース・自動テストのソース (xUnit の `Trait`、`build/tests` の `Invoke-TestCase`)・テストの結果 (`*.trx`) から作る (`dotnet run --project tools/TestCoverage`。出力は `docs/test/test-coverage.md`)。CI の `coverage` ジョブは `--enforce-phase <完了したフェーズ>` で実行し、そのフェーズまでに上の 3 つのどれかがあれば失敗にする。Core のテスト (`TestSpec/CoverageTests`) も、完了したフェーズ (`CompletedPhase`) について同じことを確かめる。フェーズが完了したら、この 2 か所の値を上げる。
- 機能を実装するプルリクエストでは、その機能の「自動」のテストケースすべてに対応する自動テストを含める。含まない場合は CI を失敗させる (フェーズごとに有効にする)。

### 6.3 データエンジンのテスト

データエンジンは誤りがデータの破壊につながるため、特に厚くテストする。

- **基準モデルとの比較**: 同じ操作列をピースツリーと単純な実装 (バイト配列) の両方に適用し、結果が一致することを FsCheck で無作為な操作列 (挿入・削除・上書き・塗りつぶし・Undo・Redo・保存) について確認する。
- **巨大ファイル**: スパースファイル (実際のディスク使用量はほぼゼロ) で 100 GB・2 TB・8 EB 近くのファイルを作り、境界のオフセット (2^31、2^32、2^53 の前後) での読み書きを確認する。
- **異常系**: 読み込みエラー・書き込みエラー・空き容量不足・途中での強制終了を、テスト用のデータソースで再現する (7.2)。

### 6.4 ディスク・プロセスのテスト

- ディスク: CI で仮想ディスク (VHDX) を作って接続し、物理ディスクとして読み書きする。テスト後に必ず切断・削除する。実際のディスクには書き込まない。
- プロセスメモリ: `tools/TestTarget` を起動し、既知の内容を書いたメモリを読み書きする。
- USB メモリ・SMART など実機が必要なものは手動にする。

### 6.5 UI テスト

- FlaUI で UI オートメーション経由で操作する。座標によるクリックは使わない (要素は `AutomationId` で探す)。そのため、すべての操作対象の要素に `AutomationId` を付ける (09 の UI-50 と合わせる)。
- テストごとに新しい設定フォルダで起動する (8.3 の `--test-profile`)。
- 失敗したときは、スクリーンショットとアプリのログを CI の成果物に保存する。

### 6.6 性能テスト

- CI の共有ランナーは性能が安定しないため、性能テストは毎晩、同じ環境で実行し、前回からの悪化 (既定 20% 以上) を警告にする。00-overview 11.1 の目標値を超えた場合は失敗にする。
- データエンジンの性能テスト (`HexEditor.Performance.Tests`) は、アプリを起動せずにエンジンを直接計る。テストケースの環境が「性能テスト用の固定の環境」のもの (フレームの間隔、2 回目の起動、OS のキャッシュを消す計測など) は、環境変数 `HEXEDITOR_PERF_MACHINE=1` の計測機でだけ実行し、それ以外ではスキップする。
- UI の性能テスト (`HexEditor.UITests` の `Category=Performance`) は、診断表示の記録 (7.2「描画の計測ログ」) を CSV に書き出して集計する。計測にはテスト用の Release ビルド (`-p:HexTestHooks=true`) を使い、`HEXEDITOR_APP_EXE` で指定する。

## 7. テストデータ

### 7.1 テストデータ生成ツール

テストに使うファイルは、リポジトリに入れずにツールで生成する。

- `tools/TestDataGen` が、[test-data.md](test-data.md) に載っているすべてのテストデータを生成する。同じ ID からは常に同じ内容を作る (乱数の種を固定する)。
- 巨大なファイルはスパースファイルとして作り、実際のディスク使用量を抑える。
- 使い方:
  - `TestDataGen all <出力先>`: すべて生成する。
  - `TestDataGen <ID> <出力先>`: 1 つだけ生成する。
  - `TestDataGen list`: ID と説明の一覧を表示する。
- 自動テストは実行前に必要なデータを自動で生成する。手動テストでは手動テスト支援ツールが自動で生成する (8.2)。

### 7.2 異常を再現する仕組み

テスト用のビルド (Debug ビルドと、テスト用に作る Release ビルド) だけに、異常を再現する仕組みを入れる。製品版には含めない。

| 仕組み | 内容 |
| --- | --- |
| 遅いデータソース | 読み込みに指定の遅延を入れる (仮表示・進捗表示の確認用) |
| 読み込みエラー | 指定の範囲の読み込みを I/O エラーにする |
| 書き込みエラー・空き容量不足 | 保存中の指定のバイト位置で失敗させる |
| 強制終了 | 保存中・自動保存中・設定ファイルの書き込み中 (一時ファイルへの書き込み中・置き換えの直前・直後) の指定の時点でプロセスを終了する |
| 更新元の差し替え | テスト用のビルドだけが設定 `test.update.source` を読み、更新の確認・ダウンロードをテスト用のリポジトリに向ける (10 の PKG-17 の 8)。Velopack の再起動後も有効にするため、`--test-hooks` ではなく設定で指定する |
| 外部変更 | 開いているファイルを外部から変更する |
| 時刻の固定 | 日時の表示・ログのテスト用に時刻を固定する |
| メモリ不足の通知 | OS のメモリ不足の通知を受けたときと同じ処理を起こす |
| 未処理の例外 | 指定の処理の中で未処理の例外を起こす (復旧用データの書き出しの確認用) |
| 仮想のデータソース | 実際のファイルなしに、0〜2^63−1 バイトの任意の長さ (長さ固定・可変を選べる) のデータソースを作る。値はオフセットから計算する |
| 描画内容の読み出し | Hex ビューが描いた内容 (セルごとの文字・文字色・背景色・線・色の層 (VIEW-17)・行のオフセット・カーソル) を UI オートメーション経由で読み出す |
| 地域設定・タイムゾーンの上書き | OS の設定を変えずに、アプリの地域設定とタイムゾーンを指定する |
| ファイルのダイアログの差し替え | 「開く」「名前を付けて保存」の標準のダイアログ (前面に出てフォーカスを奪う) の代わりに、指定のパス (またはキャンセル) を返し、呼ばれたことをログに記録する |
| 空き容量の上書き | 保存先・ジャーナルの置き場所のボリュームの空き容量を指定の値にする (空き容量不足の確認用。ENG-25) |
| 外部の起動の記録 | ブラウザなどの起動 (URL を開く) を行わず、URL をログに記録する (テスト中に他のアプリを前面に出さない) |
| 表示倍率の変更の再現 | モニターの表示倍率 (DPI) の変更を受けたときと同じ処理を起こす |
| 描画の計測ログ | フレームの間隔と、入力から画面反映までの時間を記録して出力する (VIEW-04) |

### 7.3 共通の判定基準

仕様書の数値でない表現は、すべてのテストケースで次のように判定する。

| 仕様書の表現 | 判定 |
| --- | --- |
| 60 fps を保つ | フレームの間隔の 99 パーセンタイルが 16.7 ms 以下、かつ最大が 50 ms 以下 |
| UI が固まらない | キー入力から画面反映までが 50 ms 以下 (00-overview 11.1) |
| メモリがほぼ増えない / 増えない | 操作の前後のプライベートバイトの差が 50 MB 以下 |
| すぐに開く / すぐに表示する (数値の指定がないもの) | 500 ms 以下 |
| 同程度の速さ | 比べる対象との差が 10% 以内 |
| KB / MB / GB / TB (テストでの解釈) | 1024 の累乗 (KiB / MiB / GiB / TiB) とする |

これらは、コマンドラインの `--test-hooks <設定ファイル>` と、テスト用のメニュー (8.4) から有効にする。

## 8. 手作業のテストをスムーズにする仕組み

### 8.1 手動テスト支援ツール (ManualTestRunner)

手動・半自動のテストケースを 1 件ずつ表示し、結果を記録する小さなアプリ。

| 機能 | 内容 |
| --- | --- |
| テストの選び方 | 「スモーク」「リリース前」「変更した機能に関係するもの」「指定のフェーズ」「指定の機能 ID」「前回失敗したもの」で絞り込む |
| 表示 | テストケースの前提・手順・期待結果を、HexEditor の横に常に前面で表示する。手順は 1 つずつチェックできる |
| 準備 | 「準備」ボタンで、テストデータの生成、テスト用の設定フォルダの作成、必要な引数での HexEditor の起動を行う (8.2) |
| 記録 | 「合格」「不合格」「保留」「対象外」を 1 クリックで付ける。不合格のときは、画面のスクリーンショット、HexEditor のログ、環境の情報 (OS・言語・倍率・配布形態・版) を自動で添付し、コメント欄を開く |
| 半自動 | 自動で撮ったスクリーンショットを並べて表示し、合否だけを付ける (例: 23 言語の同じ画面を一覧で確認する) |
| 再開 | 途中で止めても、次回は続きから再開できる |
| 報告 | 結果を Markdown と JSON で出力する。不合格のものは GitHub の Issue の下書きを作る (送信は人が確認してから) |
| 所要時間 | 選んだテストケースの所要時間の合計と、残り時間を表示する |

- テストケースは `cases/*.md` を直接読み込む。そのため、4 章の書式を厳密に守る。書式の誤りは CI で検査する。

### 8.2 準備の自動化

手動テストケースの「前提」は、手動テスト支援ツールが次の方法で作れるように書く。

- テストデータの生成 (7.1)
- テスト用の設定フォルダの作成と、そこに置く設定 (例: 「1 行 32 バイト」「アラビア語表示」)
- HexEditor の起動引数 (ファイルを開く・オフセットを指定する・言語を指定するなど。08 の AUTO-37)
- 異常を再現する仕組みの有効化 (7.2)

手動でしかできない準備 (USB メモリを挿す、管理者として実行するなど) だけを、テストケースの「前提」に手順として書く。

### 8.3 テスト用の起動オプション

| オプション | 内容 |
| --- | --- |
| `--test-profile <フォルダ>` | 設定・最近使ったファイル・セッション・復旧用データをすべて指定のフォルダに置き、普段使いの設定に影響しない |
| `--ui-lang <言語>` | 表示言語を指定して起動する |
| `--pseudo-locale` | 疑似翻訳で起動する (09 の UI-46) |
| `--test-hooks <設定ファイル>` | 異常を再現する仕組みを有効にする (テスト用のビルドだけ) |

これらは機能仕様書の 08 の AUTO-37 で定めている。`hexed` 共通の `--lang` はコンソールのメッセージの言語で、`--ui-lang` とは別。

### 8.4 テスト用のメニュー

テスト用のビルドだけに「テスト」メニューを置き、次を行えるようにする。

- 異常を再現する仕組みの切り替え (7.2)
- 現在の状態の表示 (カーソル位置、ピースの数、キャッシュの使用量、メモリの使用量、Undo の件数)
- ログの表示と保存
- 設定フォルダを開く、設定の初期化

### 8.5 仮想マシンの用意

- Windows Sandbox の設定ファイル (`.wsb`) を、クリーンな Windows でのインストールのテスト、日本語・アラビア語の環境のテスト用に `tools/sandbox/` に置く。起動すると、最新のビルドとテストデータが自動で置かれる。

## 9. テストの実行計画

| タイミング | 自動テスト | 手動テスト |
| --- | --- | --- |
| プルリクエストごと | 単体・結合・UI (優先度「高」) | なし |
| 毎晩 | すべての自動テスト (性能・国際化・アクセシビリティ・配布を含む) | なし |
| 毎週 | ファジング | なし |
| プレビュー版のリリース前 | すべて | スモーク (優先度「高」の手動・半自動。目安 1 時間以内) |
| 安定版のリリース前 | すべて | すべての手動・半自動のうち、そのリリースまでのフェーズのもの |

## 10. 合格の基準

リリースしてよい条件:

1. すべての自動テストが合格している。
2. 実行計画 (9 章) の手動テストがすべて「合格」または「対象外」になっている。
3. 「保留」のものがあれば、理由と対応方針が記録されている。
4. test-coverage.md で、そのリリースまでのフェーズの受け入れ基準に、テストケースのないものがない。

## 11. 不具合の記録

- 不具合は GitHub の Issue に記録し、テストケース ID と機能 ID をラベル・本文に入れる。
- 不具合を直したら、その不具合を再現する自動テストを追加する (自動化できない場合は手動テストケースを追加する)。
